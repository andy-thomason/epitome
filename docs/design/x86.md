# x86-64: a plan

This is the plan for an x86-64 target: how its instructions are written in
a description, and what the code generator's Rust must learn first. The
aim is the same as for AArch64 and RISC-V. The description names every
instruction, register, CPU and relocation, and the Rust names none.

[targets.md](targets.md) lists what the Rust still assumes about a machine.
x86 breaks most of it:

- instructions are 1 to 15 bytes, not one 32-bit word;
- most instructions are two-address, and some use fixed registers
  (`div` uses `rax` and `rdx`; a variable shift's count is in `cl`);
- almost every arithmetic instruction can read or write memory, with a
  full addressing mode;
- most arithmetic writes the flags;
- `call` pushes the return address, so there is no link register.

The survey behind this plan (file and line references against `main` at
`bacf04f`) is summarised in the last section.

## Instructions in the description

### The encoding: the `"enc"` language, extended

x86's encoding rules are written in the description, in the same `"enc"`
language as AArch64's and RISC-V's, extended in three general ways. The
Rust learns no x86 rule: not when a REX prefix is needed, not that `rsp`
as a base needs a SIB byte, not when a displacement fits in a byte.

**1. Pieces.** An encoding is a list of pieces separated by `|`. Each is
written most significant bit first, as now, and is a whole number of
bytes. A piece of several bytes is emitted little-endian. AArch64's and
RISC-V's encodings are single 32-bit pieces and are unchanged. An x86
immediate is a piece of its own (`imm:s32=c`), as are the
displacements.

**2. Alternatives, guards and optional parts.**

- `{ a ; b ; c }` lists alternatives. The first, in the order written,
  that fits is used.
- `{ a ; }` makes `a` optional: the empty alternative.
- An alternative fits when its fields encode and decode back to the same
  operands. That is the round trip that already decides which immediates
  fit, so the shortest form that holds the operands wins:
  - a REX prefix only when a register is 8 or above;
  - a displacement in one byte when it fits;
  - a short jump when the target is near.
- `if(expr)` guards an alternative where two forms decode to the same
  operands but mean different things. It is checked when encoding and
  when decoding.
  - Byte registers 4–7 are `spl`…`dil` with a REX prefix and `ah`…`bh`
    without one.
  - `r/m` = 4 means a SIB byte follows; with mod 00, `r/m` = 5 means
    RIP-relative.
- An expression can read `end`, the address just past the instruction
  (and `pc`, its start). A branch's displacement is `dest-end`.
- A relocated field's addend comes from its expression: `sym-end` gives
  `R_X86_64_PC32`'s -4, and more after an immediate.

**3. Fragments.** A named piece of encoding is defined once in the
description and used by name, with its operands as arguments:

```llvm
!target.encodings = !{!3000, !3001, !3002, !3003}
; The REX prefix, when one is needed (or always, for REX.W).
!3000 = !{!"rex", !"w r x b",
  !"{ if(w==0) ; 0100 W:1=w R:1=r>>3 X:1=x>>3 B:1=b>>3 }"}
; ModRM for a register operand.
!3001 = !{!"rr", !"r b", !"11 reg:3=r&7 rm:3=b&7"}
; ModRM, SIB and displacement for a memory operand m: [base + index*scale + disp], or sym(%rip).
!3002 = !{!"rm", !"r m", !"{
    if(m.rip)                              00 reg:3=r&7 101 | disp:s32=m.sym+m.disp-end ;
    if(m.noindex & (m.base&7)!=4 & (m.base&7)!=5 & m.disp==0)
                                           00 reg:3=r&7 rm:3=m.base&7 ;
    if(m.noindex & (m.base&7)!=4)          01 reg:3=r&7 rm:3=m.base&7 | disp:s8=m.disp ;
    if(m.noindex & (m.base&7)!=4)          10 reg:3=r&7 rm:3=m.base&7 | disp:s32=m.disp ;
    if((m.base&7)!=5 & m.disp==0)          00 reg:3=r&7 100 | ss:2=log2(m.scale) idx:3=m.index&7 base:3=m.base&7 ;
                                           01 reg:3=r&7 100 | ss:2=log2(m.scale) idx:3=m.index&7 base:3=m.base&7 | disp:s8=m.disp ;
                                           10 reg:3=r&7 100 | ss:2=log2(m.scale) idx:3=m.index&7 base:3=m.base&7 | disp:s32=m.disp }"}
```

An instruction then reads close to the manual's opcode column:

```llvm
; ADD r/m64, r64: REX.W + 01 /r
define i64 @ADD64rr(i64 "reg"="r64" "tied" %a, i64 "reg"="r64" %b)
    "enc"="rex(1, b, 0, d) | 00000001 | rr(b, d)" "asm"="addq {b}, {d}" "clobbers"="flags" {
  %r = add i64 %a, %b
  ret i64 %r
}

; ADD r64, r/m64: REX.W + 03 /r
define i64 @ADD64rm(i64 "reg"="r64" "tied" %a, ptr "mem" %m)
    "enc"="rex(1, d, m.index, m.base) | 00000011 | rm(d, m)" "asm"="addq {m}, {d}" "clobbers"="flags" {
  %v = load i64, ptr %m
  %r = add i64 %a, %v
  ret i64 %r
}

; JE rel8 or rel32: 74 cb, or 0F 84 cd.
define void @JE(i1 "cond" %c, ptr "label" %dest)
    "enc"="{ 01110100 | rel:s8=dest-end ; 00001111 | 10000100 | rel:s32=dest-end }" … 
```

VEX and EVEX are fragments too. Their inverted register bits are
expressions (`R:1=1-(r>>3)`, `vvvv:4=15-v`), and VEX's two-byte form is an
alternative to the three-byte one, so it is used where it can hold the
operands.

Checked against `llvm-mc` (LLVM 18 on mandelbrot), the encodings the
fragments must give:

```
addq  %rsi, %rdi                   48 01 f7
addq  (%rdi,%rsi,8), %rax          48 03 04 f7
addq  $5, %rax                     48 83 c0 05
addq  $1000, %rax                  48 05 e8 03 00 00
addq  %r9, %r8                     4d 01 c8
leaq  16(%rdi), %rax               48 8d 47 10
idivq %rcx                         48 f7 f9
movabsq $0x1122334455667788, %rax  48 b8 88 77 66 55 44 33 22 11
movq  foo@GOTPCREL(%rip), %rax     48 8b 05 <rel32>
vfmadd231ps %zmm2, %zmm1, %zmm0    62 f2 75 48 b8 c2
vfmadd231ps 64(%rax){1to16}, %zmm1, %zmm0   62 f2 75 58 b8 40 10   (disp8 x 64)
```

Decoding is the same language run backwards:

- the disassembler indexes each entry's alternatives by their first
  literal byte;
- it tries those that start with the bytes it reads;
- it keeps one whose operands encode back to the same bytes.

### Operands

**Registers.** These are views of three files, as AArch64's `w` and `x`
are views of one:

| File | Classes |
| --- | --- |
| `r` (16) | `r64` (`rax` … `r15`), `r32`, `r16`, `r8` (`al`, `cl`, … `sil`, `dil`, `r8b` …; never `ah` … `bh`) |
| `v` (32) | `xmm`, `ymm`, `zmm`; registers 16–31 only with EVEX |
| `k` (8) | AVX-512 masks |

**Fixed registers.** A class can name a part of its file. A class of one
register is a fixed operand:

```llvm
!1020 = !{!"rax64", !"file", !"r", !"bits", !"64", !"holds", !"int", !"members", !"rax"}
!1021 = !{!"cl8",   !"file", !"r", !"bits", !"8",  !"holds", !"int", !"members", !"cl"}

; IDIV r/m64: rdx:rax / b, quotient in rax, remainder in rdx.
define { i64, i64 } @IDIV64r(i64 "reg"="rax64" %lo, i64 "reg"="rdx64" %hi, i64 "reg"="r64" %b)
    "enc"="rex(1, 0, 0, b) | 11110111 | rr(7, b)" "asm"="idivq {b}" "result"="rax64" "result2"="rdx64" "clobbers"="flags" { … }

define i64 @SHL64rCL(i64 "reg"="r64" "tied" %a, i8 "reg"="cl8" %n)
    "enc"="rex(1, 0, 0, d) | 11010011 | rr(4, d)" "asm"="shlq %cl, {d}" "clobbers"="flags" { … }
```

The same `members` gives `xmm0`–`xmm15` (what SSE and VEX can encode) as
a class apart from all 32.

**Memory operands.** A `ptr "mem"` operand is a whole addressing mode,
`[base + index×scale + disp32]` or `sym(%rip)`. The body reads or writes
through it:

```llvm
define i64 @ADD64rm(i64 "reg"="r64" "tied" %a, ptr "mem" %m)
    "enc"="rex(1, d, m.index, m.base) | 00000011 | rm(d, m)" "asm"="addq {m}, {d}" "clobbers"="flags" {
  %v = load i64, ptr %m
  %r = add i64 %a, %v
  ret i64 %r
}
```

The description says once, in `!target.addressing`, which forms exist:

- the base and index classes (no `rsp` as an index);
- the scales: 1, 2, 4, 8;
- the displacement: a signed 32-bit value;
- PC-relative symbols.

Selection folds what `prepare` already writes,
`gep(gep(base, shl(index, s)), C)`, into the operand. The alternative is
one generated entry per instruction per addressing form, with no Rust:
about five times the entries, and patterns the trie must try one by one.
One `"mem"` operand keeps the description to one entry per instruction
form.

**Generated entries.** As AArch64's vectors are made by `gen_vectors.py`,
a script writes the regular families from a compact table. For each
mnemonic and width, it writes the `rr`, `rm`, `mr`, `ri`, `mi` and `ri8`
forms:

- `add`, `adc`, `sub`, `sbb`, `and`, `or`, `xor`, `cmp`;
- `mov`, `test`, `lea`;
- `movzx` and `movsx`;
- the shifts and rotates;
- `imul`;
- `setcc`, `cmovcc` and `jcc`, one per condition;
- SSE and AVX arithmetic over `ss`, `sd`, `ps`, `pd` and the integer lanes.

Hand-written entries cover:

- `div` and `idiv`;
- `cqo`/`cdq`;
- `cpuid`-like oddities;
- `push`, `pop`, `call`, `ret`;
- the string instructions, if wanted.

### Flags

EFLAGS is a lazy comparison, as NZCV is. `cmp` and `test` are flag
setters (`"sets"`), and `cc.l`, `cc.b`, `cc.e` … are condition forms
(`"reads"` names the flags each reads: `l` reads SF and OF, `b` reads CF).
What is new is that most other instructions clobber the flags. They say
so (`"clobbers"="flags"`), and the passes that assume only setters, calls
and asm write the flags learn to read it (`peephole::redundant_compares`).
At first only `cmp` and `test` feed branches. Letting `sub`, `and` or `add`
set flags that a branch then uses is an optimisation for later. It needs
an instruction that has a register result and also sets flags.

Floating-point compares (`ucomisd`) set ZF, PF and CF. `oeq` is
ZF and not PF, and `une` is not ZF or PF, so they become two conditions.
`prepare` splits `oeq`/`une` for x86 where it splits `one`/`ueq` for
AArch64 (a parameter, `fcmp-split`).

### Roles

The three-address roles map onto `lea`:

- `addi` is `lea d, [n + imm]`, and `add` is `lea d, [n + m]`. Both are
  true three-address instructions that leave the flags alone, as frame
  code wants.
- Two-address roles (`shli`, `sub`) are emitted with the tied copy
  inserted, as patterns already are. That is a small change in Rust.

New roles:

| Role | Use |
| --- | --- |
| `push`, `pop` | frames |
| `addr` (`lea sym(%rip)`), `got` (`mov sym@GOTPCREL(%rip)`) | a global's address in one instruction, where AArch64 takes two (`addr.hi`/`addr.lo`) |
| `nop` | padding in `.text` (x86 pads with NOPs) |
| `jump.short`, `jcc.short` | the rel8 forms for branch relaxation |

## What the Rust must learn first

These are generic changes, made with AArch64 and RISC-V passing
unchanged, before any x86 entry is selected.

1. **Bytes, not words, and the extended `"enc"`.**
   - Pieces, alternatives, guards, fragments and `end`, in `enc.rs`.
   - `MFunc::bytes` comes from the encoding.
   - `encode_function` returns bytes.
   - These follow from that:
     - the object writers;
     - the assembler: a sizing pass;
     - objdump: a byte-stream decoder;
     - the check harness.
   - Fixups record where in the instruction their field is, and the
     addend their expression gives.
   - `.text` padding uses the `nop` role.
   - RISC-V's compressed instructions become possible too: 2-byte pieces.
2. **Layout to a fixed point.** With alternatives, an instruction's
   length depends on where its target is. Layout starts with every branch
   at its shortest and lengthens what does not reach until nothing
   changes. Today it only inverts a conditional branch around a jump.
3. **Classes that name part of a file** (`members`), with the register
   allocator picking only from an operand's class. Fixed-class operands
   are copied into and out of their registers around the instruction, as
   call arguments are today.
4. **Clobbers that are not calls.**
   - Today any `imp_defs` makes an instruction count as a call:
     - for the allocator's preference for callee-saved registers;
     - for the frame record;
     - for the flags.
   - A separate list of clobbered registers fixes this. SME's `smstart`
     wants it too.
5. **An instruction with a register result that also sets flags**: later,
   for `sub` + `jcc`.
6. **Frames with the return address on the stack.**
   - A convention parameter, `return-address` = `stack`.
   - At entry, `rsp` is 8 modulo 16.
   - Incoming arguments sit 8 bytes further up.
   - The CIE's rule is `rsp + 8`, with the return address column `rip`.
   - The frame pointer is set by `push rbp`, then `mov rbp, rsp`.
   - A red zone is a later option.
7. **SysV x86-64.**
   - Results in `rax`, `rdx`, `xmm0`, `xmm1`: an explicit list; today
     they follow the arguments.
   - `al` set to the number of vector registers used by a variadic call.
   - `__va_list_tag`, `va-list` = `sysv64`, beside `aapcs64`.
8. **Constants and globals in one instruction**: `mov $imm32`, `movabs`,
   `lea sym(%rip)`.
9. **ELF x86-64.** `EM_X86_64` (62), and relocations as data:
   - `R_X86_64_64`, `PC32`, `PLT32`;
   - `GOTPCREL`, `REX_GOTPCRELX`;
   - the TLS ones.

   Mach-O x86-64 is left out, as no machine here runs it.

## Where the instructions come from

As for RISC-V, which was generated from riscv-opcodes with LLVM's
assembler as its check:

- **The source:** Intel XED's instruction tables (Apache-2.0), read by
  `gen_xed.py`. Each XED form (prefixes, opcode map, ModRM fields,
  immediates, VEX and EVEX bits, operands) becomes an entry in the
  `"enc"` language over the fragments of `00-base.ll`. The fragments
  themselves follow the Intel SDM and the AMD APM.
- **The AT&T templates:** found by asking LLVM. `discover_att.py`
  assembles every entry with a placeholder template using our own
  encoder, and turns what `llvm-objdump` reads back into a template
  (`att.txt`). Entries written alike merge into one with the encodings as
  alternatives.
- **llvm-mc's choices:** where several encodings are right, the one
  `llvm-mc` writes comes first. That is shortest first; then, among those
  as short, the one it writes (`order_llvm.py`, `order.txt`). For VEX,
  operations it commutes (`commute_llvm.py`, `commute.txt`) and moves
  written by their store form get the two-byte prefix. What `llvm-mc` 18
  does not assemble is left out (`rejects.txt`).
- **The check:** `tests/x86.rs` samples every entry at its edges, checks
  that it round-trips through `epitome-as` and `epitome-objdump`, and,
  where `llvm-mc` is installed, that the code and relocations are
  `llvm-mc`'s.
- **Running:** mandelbrot is x86-64 Linux (Zen 5: AVX2, AVX-512 with BF16
  and VNNI). `tests/programs.rs`, `abi.rs` and `inline_asm.rs` can run
  natively there, as they do on the Mac for AArch64, once they pick the
  host's target rather than assuming AArch64.

## Progress

**Stage 0, done in part (22 October 2026).** Item 1 of the list above:

- `enc.rs` reads pieces, alternatives, guards, fragments, zero-width
  fields, comparisons and `end`. An encoding is a list of alternatives,
  each a list of pieces; encoding and decoding work on bytes.
- `encode_function` returns the bytes, where each instruction starts, and
  fixups with their field's place and addend. `mir::sizes` finds lengths
  that depend on distances (short and long branches) by growing them from
  their shortest until all fit; `set_sizes`, after layout, records them for
  what measures code without encoding it (unwind and exception tables).
- The assembler keeps each instruction's length by its line, starting at
  the target's shortest, and assembles again with the lengths that turned
  out longer until none do.
- The disassembler reads a byte stream; entries are tried by the literal
  bits of their first byte (an index made once per target).
- A relocated field holds zero in the object (ELF's RELA addend holds the
  rest), and objdump shows the symbol less what the field adds itself.

AArch64 and RISC-V pass every test unchanged. Items 2–4 (layout of
x86's own branches, `members`, clobbers) come with selection.

**Stage 1, the integer instructions as `"asmonly"`.** `targets/x86_64/`
is built in (`--target=x86_64`, or a triple `x86_64-...`). `gen_x86.py`
writes 1,208 entries: the ALU group, `mov` (with `movabs`), `lea`,
`test`, the unary group, `imul`'s three forms, the shifts and rotates, the
widening moves, `setcc`, `cmovcc`, `jcc`, `jmp`, `call`, `ret`, `push`,
`pop`, `bswap`, and the bit counts, in each width and each memory form.
Sample lines at the edges (every register in each place, immediates and
displacements at their limits, RIP-relative symbols, near and far
branches): 16,889 lines assemble to the same 98,656 bytes and 2,804
relocations as `llvm-mc`'s, and disassemble as `objdump` reads them (up
to how each writes numbers, and `rolq %rax` for `rolq $1, %rax`).

**Stage 1, vectors.** `81-vector.ll`, from the same script: 1,047 entries
of SSE (the four float types' arithmetic, logic, moves, compares and
conversions; integer lanes; shuffles; moves between files), AVX and AVX2
on 128 and 256 bits (arithmetic, FMA's three forms, moves, broadcasts),
and AVX-512 on 512 bits (arithmetic and FMA with `{1to16}` broadcasts,
moves, integer lanes, VNNI's `vpdpbusd`/`vpdpwssd`, BF16's `vdpbf16ps`
and `vcvtne2ps2bf16`). The fragments `vex`, `vexm`, `evex`, `evexr` and
`evexm` write the prefixes; `rm` takes EVEX's disp8×N scale as a
parameter. With the integer entries: 37,346 lines, the same 255,643 bytes
and 8,076 relocations as `llvm-mc`'s.

What writing them taught:

- **An operand only a guard reads cannot be decoded.** The accumulator's
  short forms (`05 id` for `add $c, %rax`) say `a:0=d` (a zero-width
  field: d is 0, and decoding sets it), not `if(d==0)`.
- **Decoding must agree with every field.** A register is in `r>>3` (REX)
  and `r&7` (ModRM); a memory operand's absent index, 4, is in `x>>3` and
  in a zero-width `x-4`. Each field that holds the operand alone proposes
  a value, and the first that all of them hold is taken.
- **RIP-relative needs its own REX.** Base 16 does not fit REX.B, so
  `rexm` uses a REX with neither X nor B for it.
- **Byte registers need REX for spl-dil.** Without one, 4-7 are ah-bh;
  the byte forms' REX is present whenever a byte register is 4 or more.
- A zero-width field alone in a piece (before a prefix left out) joins the
  next piece.
- **Inverted bits are slices too.** VEX and EVEX store register bits
  inverted (`R:1=(r>>3)^1`); decoding puts a register back from slices
  that may be flipped (`(x>>k)^c`), so xmm0-31 split over ModRM, R and R'
  decode exactly.
- **llvm-mc chooses shorter forms, and the description can say so.** A
  commutative VEX operation whose second source needs the three-byte
  prefix and whose first does not has its sources swapped for the
  two-byte one; a register move uses its store opcode for the same
  reason. Both are alternatives in the entry: `{ if(s<8) plain ; if(v<8)
  swapped ; plain }`. The assembler checks a line against the
  alternative it used (`Instr::decode_alt`), as the swapped bytes read
  back, rightly, as the swapped operands.
- `movq` between memory and xmm is its own instruction (`F3 0F 7E`,
  `66 0F D6`), not the GPR form's.

**Stage 1, the whole instruction set, from XED.** `02-xed.ll` (first of the
files, so that the assembler prefers its encodings) replaces the
hand-written tables: 32,659 entries, every form `llvm-mc` 18 assembles of
the legacy, VEX and EVEX encodings. That covers integer, x87, MMX, SSE to
4.2, AVX, AVX2, FMA, FMA4, F16C, BMI, AVX-512 (all widths, masks and
zeroing, broadcasts, rounding and `{sae}`, FP16, BF16, VNNI), AMX, and
the system instructions. 931,639 sample lines assemble to the same
8,086,731 bytes and 220,762 relocations as `llvm-mc`'s.

Left out: APX, XOP, and gathers and scatters (VSIB); AVX10.2 and other
forms newer than `llvm-mc` 18; aliases `llvm-mc` does not read; and
`ah`-`bh`.

What it took in the Rust, all general:

- **Lazy encodings.** A description can ask for its encodings to be
  parsed when first used (`"lazy-encodings"`), as x86-64's does: tens of
  thousands load in a fraction of a second. `--check-target` parses them
  all first. `"instruction-unit"` gives the shortest instruction's length.
- **A disassembler index** by the first byte, then by the first byte
  after it whose bits are all literal (the opcode, after a VEX or EVEX
  prefix), each alternative's literal bits over its first 8 bytes checked
  at once.

Its size: 10.6 MB of description, 466 KB compressed. Most of it comes
from writing each memory form and mask as its own entry. A memory
operand and a mask written by the Rust (the "mem" operand of the plan)
would cut it about ninefold.

**Stages 2, 3 and 6 (23 October 2026).** `gen_sel.py` writes
`10-integer.ll`, the entries selection uses (each `"nodecode"`: the XED
entries read code back), and `70-abi.ll` is System V's convention. On
mandelbrot:

- `tests/x86_programs.rs` compiles every C program of `tests/programs`,
  and `tests/x86/` (`long double`, SSE2's vector operations), at `-O0`,
  through epitome-opt, at `-O2`, vectorised, and `-O2 -fPIC` into a
  shared library; runs each against clang's build; checks clang's
  assembler makes the same code and relocations of our assembly, and that
  epitome-objdump reads our object back as it;
- `x86_sqlite.rs`: SQLite's three builds answer as clang's does, the
  vectorised one byte for byte clang's assembler's;
- `x86_unwind.rs`: C++ exceptions through and into our code;
- `rust.rs`, `inline_asm.rs` (`tests/asm/x86.c`), `ir.rs`, `masks.rs` and
  `bitcasts.rs` run on x86-64 Linux as on the Mac.

What selection has:

- Integers: the ALU group two-address (`"tied"`; ties are copied for
  instructions made by role too), `lea` for the code generator's own
  adds, shifts by an immediate or by `cl` (a **fixed register class**,
  `rcx`), `imul`, division through `rax` and `rdx`, `"clobbers"="flags"`
  on what writes them. Loads at a base plus a scaled index. Flags are
  `%flags`, with conditions named as x86's.
- Floats: SSE2 scalar, in `d` and `s`; `ucomisd` sets `%fflags` (or
  `%fflagsr`, swapped) whose conditions are fcmp predicates; oeq and une
  of scalars are two (`fcmp-split`). Rounding, `fmin`/`fmax` and
  `fminimum_num` are the C library's (no SSE4.1).
- Vectors (SSE2): 128 bits in `xv`, 64 in `xh` (a register's low half),
  masks in `xv` as lanes of all ones; integer and float arithmetic, every
  comparison (recipes for what SSE2 lacks), selects by masks, shifts by
  immediates, lanes, splats, halves, widening, sums across lanes;
  constants from 64-bit words. What has no instruction is done a lane at
  a time through a stack slot (`lanewise.rs`).
- Vectors (AVX2), for functions with `avx2`: 256 bits in `yv`, masks in
  `yv`; the VEX entries' encodings are taken from `02-xed.ll`. Integer
  and float arithmetic, `vpmulld`, min and max, shifts by vectors, every
  `vcmpps` predicate, `vpblendvb` and `vblendvps`, FMA (with `fma`),
  conversions, halves, `vpmovsx`/`vpmovzx`, broadcasts. (AVX-512
  functions use this tier too.)
- Memory operands: loads at a base plus a scaled index, arithmetic and
  comparisons with memory, and loads and stores of a global's own
  address RIP-relative.
- `long double` (`x86_fp80`) on the x87 (`x87.rs`): each value in a stack
  slot, each operation x87 instructions in order with the stack empty
  between them.
- Half: the C library's `__extendhfsf2` and `__truncsfhf2`.
- Atomics: `xchg`, `lock xadd`, `lock cmpxchg`, plain ordered loads, a
  sequentially consistent store as `xchg`, `mfence`.
- System V: registers and the stack, `byval`, `__int128` 16-aligned,
  `%al` for variadic calls, the `va_list`, `{ <2 x float>, float }` in
  xmm0 and xmm1, the return address on the stack (no frame record).
- Thread-locals by initial exec; symbols another module may define
  through the GOT (`R_X86_64_REX_GOTPCRELX`), so `-fPIC` code works.
- Inline assembly: the usual constraints and modifiers, AT&T's `$`, and
  aliases for what people write (`(%rax)`, `jz`).

Not yet: AVX-512's own 512-bit selection (k masks), `vpternlog` for
chains of bitwise logic over three values (planned in
[combines](combine.md), "Three-input bit functions"), shuffles beyond
splats and halves (others go a lane at a time through memory, slowly:
`rgb_gray`'s stride-3 loads), 64-bit lanes multiplied, `long double` as
arguments and results. Spilling costs more than on AArch64: linear scan
reloads a spilled value at each use, and x86 has 13 registers to
allocate, not 28. Values that are worth more take registers from those
worth less, and a copy to or from a spilled value is the load or store
itself: SQLite's stack accesses fell from 85,000 to 60,000, and at `-O2`
it runs in 1.47 times clang's time (from 1.85).

## Decisions

Settled on 22 October 2026:

| Question | Decided |
| --- | --- |
| Assembly syntax | AT&T, as clang, `llvm-mc` and `objdump` write it on Linux. |
| Memory operands | One `"mem"` operand per entry: the addressing forms are a fragment in the description, and selection folds addresses into it. |
| Where the encoding rules live | In the description, in the extended `"enc"` language. The Rust gets only general machinery, and as little as possible. |
| Where the description lives | Built in, as AArch64 is: `codegen/targets/x86_64/`, read with `include_str!`. |
| Object format | ELF only. |
| The instruction set | All of it that `llvm-mc` 18 can check, generated from Intel XED's tables (decided later the same day). |

## The survey, in short

Against `main` at `bacf04f`:

- **Four-byte words:**
  - `enc.rs`: `Encoding { mask: u32, value: u32 }`; a parse fails unless
    it is 32 bits.
  - `mir.rs:227-235`, `:500-543`: sizes and encoding.
  - `object.rs:264-273`, `:317`, `:414-422`: placement, sizes, in-place
    patches.
  - `assembler.rs:700-738`.
  - `objdump.rs:409-439`.
  - `check/mod.rs:540`.
  - Labels are relative to the instruction's start
    (`mir.rs:527`, `layout.rs:233-247`, `assembler.rs:358`), and fixups
    have no addend (`object.rs:331`, `assembler.rs:743`).
- **Classes and allocation:**
  - A class is always a view of its whole file (`machine.rs:352`,
    `:585-594`).
  - The allocator chooses within a file (`regalloc.rs:308-317`).
  - Fixed registers exist only for argument copies and calls
    (`isel.rs:2240-2250`).
- **Ties:** honoured only in pattern emission (`isel.rs:1518-1533`).
  Roles emitted three-address at about 20 call sites (`isel.rs`,
  `frame.rs`, `peephole.rs:122`).
- **Implicit defs are taken for calls:** `regalloc.rs:230-232`,
  `frame.rs:63-65`, `peephole.rs:36`.
- **Flags:**
  - Setters cannot also have a result (`target.rs:794`).
  - `redundant_compares` assumes no other instruction writes the flags
    (`peephole.rs:3-49`).
  - `fcmp one`/`ueq` are split the AArch64 way (`prepare.rs:5415-5435`).
- **Frames:**
  - `lr` must be a register (`abi.rs:356`, `:384`).
  - Frame record `[fp, lr]` (`frame.rs:52-69`, `:138-141`).
  - No +8 for a return address (`frame.rs:87-89`).
  - CIE `sp, 0` (`unwind.rs:254-256`).
  - Results follow the arguments (`abi.rs:136-143`).
- **AArch64 role names in Rust:** `store.x`, `load.x`, `move.h.w`,
  `dup.{arr}`, `ins.*` (`isel.rs:14-26`, `:2145-2265`, `:3006-3017`).
- **Other fixed assumptions:**
  - Two-instruction global addresses (`isel.rs:1179-1193`).
  - TLS shapes (`prepare.rs:715-807`).
  - `va_list` (`isel.rs:2861-2911`).
  - `$x`/`$d` mapping symbols (`elf.rs:136`).
  - Mach-O arm64 only (`macho.rs:22`, `:146-158`, `:429`, `:472`).
