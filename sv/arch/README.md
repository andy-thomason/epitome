# FPGA architecture descriptions

`ice40-up5k/` describes the Lattice iCE40UP5K in the SG48 package, the FPGA
on the iCESugar board. `ice40-lp1k/` describes the iCE40LP1K in the CM36
package, the FPGA on the iCESugar-nano: the board on Amy's desk, whose
iCELink firmware reports itself as the iCESugar-nano's. It is generated by `sv/examples/ice40_arch.rs` from
the code in `sv/src/arch/ice40/`. That code is a module of epitome-sv rather
than a separate tool, so that epitome-sv can use the description and the
bitstream packer directly when it targets the part.

```bash
cargo run --release -p epitome-sv --example ice40_arch
```

It does every part in `PARTS` (`--part ice40-lp1k` does one). For each, it
reruns every source it can find and replays the records of the rest
(`--replay` replays all of them). Then it writes the description. The
same code serves both parts; only the part table (`PARTS` in
`sv/src/arch/ice40/mod.rs`) differs.

Each part's directory holds:

| File | What it holds |
|---|---|
| `record-icepack.txt` | what the `icepack` experiments found |
| `record-chipdb.txt` | what is taken from IceStorm's `chipdb-5k.txt`, in a compact form |
| `record-icebox.txt` | what the `icebox_vlog` and `icebox_explain` experiments found |
| `description.json` | the description: every fact, marked with its source, plus the cross-checks and coverage |
| `logic_cell.sv` | a SystemVerilog model of a logic cell, built from the icebox statements |
| `device.svg` | a picture of the die (see Pictures) |
| `record-board.txt` | (LP1K only) what the iCESugar-nano did in each board experiment |

The tests are in `sv/tests/ice40_arch.rs`:

```bash
cargo test --release -p epitome-sv --test ice40_arch
```

The tests that need a tool skip it when it is missing. Set
`ICE40_REQUIRE_TOOLS=1` to make a missing tool a failure. The test that
reprograms the board runs only with `ICE40_BOARD=1`.

## Pictures

`svg.rs` renders a part's description as an SVG picture of the die, and the
`ice40_svg` example writes it. The picture is drawn straight from the
records, as plain SVG with no scripts and no external fonts. Detail is in
hover text (`<title>`), so it stays readable zoomed out.

```bash
cargo run --release -p epitome-sv --example ice40_svg
```

That writes `device.svg` beside each part's description. Each picture
shows:
- every tile at its grid place, coloured by kind;
- each logic tile's eight cells and carry chain;
- each I/O tile's pads, with their package pins and, on the iCESugar-nano,
  what the board wires to them;
- the block RAMs, DSP blocks and special cells;
- how each part is known: a green outline if shown on the board, grey if
  found by experiment, and hatched if only the chip database names it.

To lay a configuration over the die, pass one of these options:
- `--asc FILE`, an `.asc` file;
- `--bin FILE`, a bitstream;
- `--experiment NAME`, one of the board experiments.

The overlay outlines the tiles the configuration sets bits in, and marks
the cells, flip-flops, RAMs and pads it uses. For example,
`ice40-lp1k/device-ram-write.svg` shows the `ram-write` experiment placed
on the LP1K.

## The flow: SystemVerilog to the board

`sv/src/synth/` and `sv/src/arch/ice40/{map,place,route,flow}.rs` take a
SystemVerilog design to an iCE40 bitstream, every stage Epitome's own, and
the `ice40_flow` example runs them. It builds for the iCESugar-nano's LP1K
unless `--board icesugar` (or `--part ice40-up5k`) picks the iCESugar's
UP5K; see [The iCESugar's UP5K](#the-icesugars-up5k) below.

```bash
cargo run --release -p epitome-sv --example ice40_flow -- sv/arch/ice40-lp1k/flow/hello.sv --check 3000 --program
```

That synthesises the module named after the file (`--top` names another),
checks the mapped cells against the interpreter for 3000 cycles, places,
routes, writes `hello.asc`, `hello.bin` and `hello.svg` to
`target/ice40_flow` (`--out` for elsewhere), and programs the board.
`--pins FILE` gives the pin constraints, lines of `port pin` or
`port[i] pin`; the default is the board's,
[`ice40-lp1k/flow/nano.pins`](ice40-lp1k/flow/nano.pins) (the boards are
`board::BOARDS`). `-D NAME=VALUE` defines a macro. `--program` first asks
`icesprog -p` which board is plugged in, and refuses another.

The stages, each in memory, with no text between them until the `.asc`:

1. **Synthesis** (`synth/lower.rs`). The elaborated design (`Design`) is
   flattened through its instances and bit-blasted into a graph of
   two-input ANDs and XORs, three-input majorities (adders' carries, kept
   for the carry chain), inputs and flip-flops. Gates are hashed and
   constants folded as they are made. `assign` (and a net declaration's
   assignment, `wire x = e;`), `always_comb`, and
   `always_ff` (or `always`) on a clock edge are synthesised, with an
   asynchronous reset to constants. There may be any number of clocks, and
   a clock may be one the design makes (a counter's bit, say). Functions
   and tasks are run inline: arguments are bound to the formals, the
   result comes from `return` or the function's own name, and outputs are
   copied back. `return`, `break` and `continue` set flags that guard the
   statements after them, so an early return from a loop (a priority
   encoder) is just logic. Procedures are run symbolically: an
   `if` runs both arms and merges what each assigned under its condition,
   so a flip-flop's enable is where it was assigned. A `case` on a value of
   up to 8 bits with constant labels becomes a decision tree on its bits,
   so a table maps to few LUTs. Others become a priority chain, and `for`
   loops with constant bounds are unrolled. Operators covered: bitwise,
   reductions, shifts (constant or not), `+ - *`, comparisons, and selects
   and part selects (constant or not). Errors point at the source: latches,
   division of non-constants, recursion, gates, combinational loops, nets
   with two drivers, and memories too big for flip-flops used in ways block
   RAM cannot do (below).

   A **memory** (an unpacked array of integral words) is kept whole, for
   block RAM. A write in a clocked process, of a whole word or a part of
   one (`mem[a][7:0] <= x`, a byte write), has an enable for each bit.
   Writes to one address in a process are one write, the later winning bit
   by bit. Writes that a BDD proves are never enabled together, such as
   those in different arms of an `if` or `case`, share the one write port.
   A register that takes a read whole (`q <= mem[a]`, under any
   conditions, no reset) becomes a read port, and the register is the
   RAM's own output register. Any number of read ports may be used. A
   memory only `initial` writes is a table: read anywhere else, it is
   logic (a decision tree on the address). A memory that block RAM cannot
   do is built from flip-flops, up to 2048 bits, and lowering starts again
   with it so. That covers a written memory read combinationally, two
   write ports at once (a register file), a reset, or two writing
   processes. Flip-flops that start at 1 are kept inverted for the iCE40
   (`Netlist::zero_inits`). Its
   contents come from `initial` blocks (constant writes, or
   `$readmemh`/`$readmemb` with the file found from the current directory)
   or from a declaration's assignment pattern.
2. **Mapping** (`map.rs`). Majorities that follow one another become carry
   chains, with the carry in from a constant, or from a signal through a
   feeder cell. The other gates are covered by 4-input cuts: up to 10 cuts
   a node, chosen for depth and then for area flow at that depth. A LUT whose
   only carry input is the carry into a chain cell (an adder's sum) goes in
   that cell's LUT, reading the carry on `in_3`. A carry read any other way
   comes out through the next cell's LUT. Flip-flops share their LUT's cell
   when nothing else reads the LUT. An enable and an asynchronous reset go
   on the cell's `cen` and `sr`. Each memory read port gets its own copy of
   the memory in RAM4K blocks, all copies written alike, since a block has
   one read port. A memory whose bits have different write enables (byte
   writes) is split into lanes first, a memory for each enable. Where a
   read may meet the word being written on the same edge, the write is
   delayed a clock through registers and such a read is served from them
   (`Netlist::delay_writes`): the board showed the block RAM unreliable
   then. A BDD can prove a design's reads never meet its write, and then
   nothing changes. A copy takes the mode (256x16, 512x8, 1024x4 or
   2048x2) that needs fewest blocks side by side. A memory deeper than 2048 words
   is first split into banks on its address's upper bits
   (`Netlist::split_mems`, a netlist-to-netlist pass, checked against the
   interpreter like the rest). The banks are as deep as gives the fewest
   blocks, then the fewest banks (`map::bank_depth`). A bank is written
   only where the upper bits pick it. Each read port registers the upper
   bits with the read and muxes the banks' outputs by them. Word bits go on
   the data pins the board found for the mode, and the contents are laid
   out by `board::ram_mode_bit`.
3. **Placement** (`place.rs`). Pins come from the constraints. RAM blocks
   go to the RAM sites nearest the middle and stay there. Carry chains
   take places 0 upwards in consecutive tiles of a column. Cells are placed
   greedily, then annealed on wirelength (half-perimeter of each net's
   tiles) with moves and swaps of cells and moves of chains. A tile's
   flip-flops must share clock, edge, enable and set/reset;
   `place::check` checks the result. A cell may be given a fixed place
   (the timing experiments use it).
4. **Routing** (`route.rs`). PathFinder over the chip database's switches:
   each signal is a tree grown from its source by cheapest paths
   (`Graph::search`, the Dijkstra search the board experiments' breadth-first
   `route` is now a case of), and nets used twice get dearer each pass until
   none is. A LUT input may land on any free pin of its cell; the table is
   permuted to match. The clock goes on a global network when its pin has a
   global buffer (D1's is network 1), with the column buffers its tiles
   (and RAMs' `RCLK` and `WCLK`) need. Any other clock, including one the
   design makes, goes on a free global network through that network's
   global buffer input. It is routed as a signal to the `fabout` of the
   I/O tile the chip database's `gbufin` names (the one nearest the
   clock's source), with the network's pad bit left clear. With
   `Options::fabric_clocks` (the example's `--fabric-clocks`), or with
   no network free, the clock is instead routed through the fabric to
   each tile's and RAM's clock input.
5. **Bitstream**. Cells, routes, I/O types (`PINTYPE_0` for an input, 3
   and 4 for an output, as the board experiments found), and the RAM
   blocks' modes (`RamConfig.CBIT_0` to `3`) and contents go into a
   `design::Design`, then the `.asc` and the bitstream come from Epitome's
   own packer.

What checks what:
- `synth::check` makes a testbench around the top module and runs the same
  random stimulus through Epitome's interpreter, through the gate netlist
  (`synth::Sim`) and through the mapped cells (`map::LcSim`, the logic cell
  as `logic_cell.sv` has it). Each cycle's outputs must agree wherever the
  interpreter's are known.
- `flow::check_routes` reads the routes back from the configured bits. For
  every sink it follows the switches set back to a net nothing drives,
  which must be its signal's source.
- `echo_ram_reverses_a_line` sends `echo_ram.sv` UART frames (a line
  with a line feed in it, bytes while it replies, an empty line) through
  all three, then decodes `tx`: the line comes back reversed.
- `icebox_reads_the_board_designs` reads each board design's bitstream
  another way: `icepack -u` makes the full-die `.asc` from it and
  `icebox_vlog` prints the Verilog it says the bits make (both IceStorm
  programs, run as black boxes). Epitome's interpreter runs that Verilog,
  its RAMs modelled by [`sb_ram40_4k.sv`](sb_ram40_4k.sv), against the
  source on the same random stimulus. This checks what the configured bits
  mean, not only the flow's own reading of them, and needs no board.
- The board, below.

The tests are in `sv/tests/ice40_flow.rs`:

```bash
cargo test --release -p epitome-sv --test ice40_flow
ICE40_BOARD=nano cargo test --release -p epitome-sv --test ice40_flow board_live
```

`ICE40_BOARD` names the board plugged in: `nano` (or `1`) or `icesugar`.
A board test skips if `icesprog -p` reports another board.

| (i) a design's clock | `hello_div.sv`: the transmitter on 12 MHz divided by 8, its clock on a global network of its own through a global buffer input | 113 | 261 whole strings in 0.5 s |

Line feeds, and bytes that arrive while it sends, are dropped; a line is kept to 511 bytes | 196 (7 chains), 99 flip-flops, 1 RAM block | 26 random printable lines (0 to 600 bytes) all back reversed |

The counter was checked through B3: the Mac sends a byte every ~0.1 s for
5 s and notes which come back. The LED (B6) blinks as well, but nothing
here watches it. Before (d) sent `\r`, it sent an `r`. SystemVerilog's
string escapes have no `\r`, and the interpreter and the board agreed, so
`hello.sv` writes the carriage return as `8'h0d`.

Before (h), the board was asked what a block RAM gives when one clock
edge reads and writes the same word. With the RAM alone, it mostly
gave the new word, but 3 bytes in 64 came back wrong, in each mode. So
the flow never lets that happen (`Netlist::delay_writes`), and (h)
checks that the old word comes back, as SystemVerilog says.

The chip database names a `fabout` net in each global buffer input's
I/O tile, but no switch from it to the global network. So the board was
asked. With the divided clock routed to `fabout` and the network's
`padin_glb_netwk` bit clear, (i) works on each of global networks 0, 2,
3, 4, 5, 6 and 7. Network 1 is D1's, so it was not tried. With `fabout`
left undriven, it is silent.

(e) delays rx by up to 2048 clocks (171 us), which the echo does not
notice; a wrong bit anywhere in a word turns it off. As a control, moving
mode 512x8's data pins up by one made it silent. For (g), swapping the
bank select's mux inputs made the echo garbled.

### Timing

`timing.rs` has a delay model measured on the board and a static timing
analysis that uses it. The example prints the analysis after each
build. No vendor's or other tool's timing data is used. The board has
one 12 MHz clock, so each delay is found by how long a path must be to
miss it. A flip-flop that toggles every clock launches through a chain of
`n` stages into one that captures it. A sticky flag is set when a capture
is not what was sent, and that turns the echo off. A binary search on
`n` finds the shortest chain that fails (`timing_calibrate`, with
`ICE40_BOARD=1 ICE40_CALIBRATE=1`). The cells are made by hand
(`timing::experiment`), and placed and routed by the flow
(`flow::build_mapped`). The switches on the routes it chose are counted.

| Experiment | Longest that passed / shortest that failed | Gives |
|---|---|---|
| LUT chain, placed by the placer (about 2 switches a stage) | 76 / 77 LUTs | together: LUT 0.30 ns, switch 0.38 ns |
| LUT chain, each stage across the die (columns 1 and 12, about 4 switches a stage) | 45 / 46 LUTs | |
| a 125-cell carry chain, then LUTs | 65 / 66 LUTs | carry 0.08 ns |
| a block RAM read, then LUTs | 76 / 77 LUTs | the RAM's clock-to-output: within a stage (about 1 ns) of a flip-flop's |

The numbers are in [`ice40-lp1k/record-timing.txt`](ice40-lp1k/record-timing.txt).
A flip-flop's clock-to-output and setup are folded into them, so the
analysis is a little optimistic. Its resolution is about a stage, about
1 ns. `timing::analyse` takes every routed connection's switches and
every cell's delay, and reports the latest arrival at a flip-flop's
input, enable or set/reset, or at a RAM input. That gives an Fmax
estimate, and separately the latest arrival at an output pin. The board
designs come out at 177 to 353 MHz against their 12 MHz.

The RAM experiment also showed that a block RAM's reads are wrong for
the first 16 to 32 clocks (1.3 to 2.7 us) after the chip is configured.
After that they read with one clock of latency, as the flow models
them. A design that needs a read in its first few microseconds should
wait. The flow does not add a wait of its own.

Not yet: latches, timing-driven placement and routing (the analysis
only reports), hold-time checks and clock skew (which matter most for a
clock routed through the fabric), packing a flip-flop with a LUT that has other
readers, and checking resource counts against Yosys and nextpnr. Running
those was blocked here, and their source is not to be read.

## The iCESugar's UP5K

The same flow builds for the iCE40UP5K-SG48 of MuseLab's iCESugar
(`--board icesugar`). Its pins,
[`ice40-up5k/flow/icesugar.pins`](ice40-up5k/flow/icesugar.pins), are from
the board's schematic (v1.5) and MuseLab's pin file for it:

| Pin | Port | What the board wires |
|---|---|---|
| 35 | `clk` | 12 MHz from the iCELink's MCO (jumper J1); a global buffer pin, network 7 |
| 4 | `rx` | the iCELink's UART transmit (jumper J5): only ever read |
| 6 | `tx` | the iCELink's UART receive (jumper J5) |
| 41, 40, 39 | `led`, `led_r`, `led_b` | the RGB LED's green, red and blue (jumper J6), through 470 ohms: low lights them |
| 18 to 21 | `sw[0]` to `sw[3]` | DIP switch S1, pulled up: closed is low |

Nothing in map, place or route was the LP1K's own: grid, tiles, RAM
sites, ports and global buffers all come from the part's records. Two
things differ, and the records said both:

- A UP5K block RAM is there only with its `RamConfig.PowerUp` bit set
  (in the `ramb` tile): `icebox_vlog` shows no RAM without it, where the
  LP1K's shows one. The flow sets it where the icebox records say a RAM
  needs it (`ram_func none omitted`).
- The read port is in the lower tile (`ramb`) and the write port in the
  upper (`ramt`), the other way round from the LP1K. The ports come from
  the icebox records' port map, so nothing changed for it.

The LP1K's bitstreams are byte for byte what they were.

No UP5K board has been on Amy's desk, so nothing here has run on one.
What checks the UP5K builds without one: `--check` (the interpreter
against the mapped cells), `flow::check_routes`, the packer against
`icepack` (`icepack` of the flow's `.asc` gives the flow's bitstream, for
every design below), and `icebox_reads_the_board_designs`, which passes
for each. As a control, leaving out the PowerUp bit made it fail
(`hello_ram`'s output unknown from the first read). `board_live` and
`timing_calibrate` take `ICE40_BOARD=icesugar` and skip unless
`icesprog -p` reports an iCESugar. Their UP5K steps, ready for a board:
(a) to (k) as on the nano, (g) also through 28 of the 30 block RAMs, and
(l) the RV32I computer below, its replies compared with its emulator's.

| `blink.sv` | 27 (a 22-cell chain) | | 1 | 6.4 ns | 0.4 s |

computer has a third of its 83.3 ns clock to spare. Build times are on Amy's Mac; most of the
computer's is routing.

### An RV32I computer

[`ice40-up5k/flow/rv32i.sv`](ice40-up5k/flow/rv32i.sv) is the bigger
design: a processor for RV32I, the RISC-V base integer instructions,
written for this from the RISC-V unprivileged specification's instruction
formats, with 8 KB of memory and a UART at 115200 baud. It takes four
clocks an instruction (fetch, decode, execute, and a fifth for a load's
alignment). Memory is 2048 words in four byte lanes (sixteen 2048x2
blocks); the register file is read twice an instruction, so it is two
copies (four blocks). The memory map is in `sv/src/arch/ice40/rv32i.rs`:
the UART's status, receive and transmit registers and the LED at
`0x8000_0000` up.

Its program, [`rv32i_demo.s`](ice40-up5k/flow/rv32i_demo.s), waits for a
byte, then prints a banner, the signature of a self-test that uses every
kind of RV32I instruction, the primes below 200 and the count below 2000
(a sieve in memory). Then it answers each line with its length, its
CRC-32 and the line reversed. `rv32i.rs` assembles it (into
`rv32i_demo.svh`, the memory's initial contents) and emulates it:

```bash
cargo run --release -p epitome-sv --example ice40_rv32i -- "Hello, iCESugar"
cargo run --release -p epitome-sv --example ice40_flow -- sv/arch/ice40-up5k/flow/rv32i.sv --board icesugar --check 3000
```

```
Epitome RV32I on the iCESugar (iCE40UP5K)
self-test fb1d535a
primes: 2 3 5 7 11 13 ... 191 193 197 199
primes below 2000: 303
> 15 3e87293b raguSECi ,olleH
```

What checks it: `rv32i_assembles` (encodings written out by hand from the
specification's formats), `rv32i_image_is_current`,
`rv32i_runs_its_program` (the mapped cells, with the UART at 8 clocks a
bit, run 228,599 clocks and send exactly what the emulator does: banner,
self-test, primes and the replies to three lines), `rv32i_builds`, and
`icebox_reads_the_board_designs` (icebox_vlog's reading of its bitstream,
1500 clocks against the source). The CRC-32s match Python's
`zlib.crc32`.

For that run, `map::LcSim` now settles the cells in one pass in
dependency order (it swept them all until nothing changed), and
`Graph::search` keeps its start nets in a set (it scanned the route tree
for each net it took); both give the same results as before.

[`rv32i.svg`](ice40-up5k/flow/rv32i.svg), the computer, and
[`echo_ram.svg`](ice40-up5k/flow/echo_ram.svg), the line echo, on the
UP5K.

## Sources, and how each fact was found

The work started as a clean room: IceStorm's, nextpnr's and Yosys's source,
chip databases and documentation were not to be read. Amy then agreed
(2026-11-14) to take a look at the chip database, a data file. So the
description has four sources, and each part of it is marked with one:

- **experiment**: IceStorm's `icepack`, run as a black box. It is the pinned
  build that `sv/tools/ice40_asc_check.py --install-only` makes. Its source
  was not read. See `experiment.rs`.
- **icebox**: IceStorm's `icebox_vlog` (`.asc` to Verilog) and
  `icebox_explain`, run as black boxes from the same pinned checkout. Only
  their output is read; a traceback would print source, so stderr is
  discarded. See `icebox.rs`.
- **chipdb**: IceStorm's chip database, a data file. It is made by running
  `icebox_chipdb` from the pinned checkout as a black box (`-5` for the
  UP5K, no flag for the 1k), and only its output is read: no source, no
  documentation. See `chipdb.rs`. For the UP5K that output is byte for
  byte the `chipdb-5k.txt` that ships in YosysHQ's OSS CAD Suite, the file
  Amy agreed to. A copy of the suite was downloaded and then deleted
  without any of it being run.
- **datasheet**: Lattice's *iCE40 UltraPlus Family Data Sheet*
  (FPGA-DS-02008) for the UP5K, and the *iCE40 LP/HX Family Data Sheet*
  (FPGA-DS-02029) for the LP1K, Table 1.1 and section 2. They give the
  resource counts and what each kind of block is.

### What the icepack experiments found

Each experiment packs `.asc` text through `icepack`'s stdin and stdout and
reads the bitstream. All of them are in `experiment.rs`. The numbers below
are the UP5K's.

For the LP1K:
- the die is 14 x 18 tiles, 248 in all, with I/O tiles on all four edges;
- there are four CRAM banks of 144 lines of 332 bits, and 16 block RAMs;
- the tiles fall into 20 layouts, because I/O tiles on the bottom and side
  edges share a bank but have different layouts;
- the framing, CRC, options and comment are the same as the UP5K's.

- **Grid**: `icepack -u` of a one-tile design lists every tile. The die is
  26 x 32 tiles, 828 in all: 660 logic, 48 io, 30 ramb, 30 ramt, 8 each of
  dsp0 to dsp3, and 28 ipcon. Every tile is 16 rows; logic, dsp and ipcon
  tiles are 54 columns wide, io tiles 18, and ram tiles 42. An `.asc` with
  no tile at all makes `icepack` fail.
- **Framing**: after an optional comment and the preamble `7e aa 99 7e`,
  each command is one byte, whose high nibble is the command and whose low
  nibble is the length of its argument. Commands 6, 7 and 8 set the width,
  height and first line of the next data; command 1 selects a bank; `01 01`
  and `01 03` are followed by CRAM or block RAM data and then two zero
  bytes. Reading every bitstream this way consumes it exactly.
- **Options**: `-s` flips bit 0 of command 9's argument, `-mN` sets command
  5's argument to N, and `-n` drops the block RAM data commands.
- **CRC**: CRC-16, polynomial 0x1021, initial value 0xffff, MSB first. It
  covers the bytes after `01 05`, up to and including the `22` of the CRC
  command. This was found by searching every command boundary, two
  polynomials and two initial values; exactly one combination fits every
  bitstream tried.
- **Comment**: `ff 00`, then each line followed by `00`, then `00 ff`.
- **CRAM**: four banks of 692 bits per line, with 336, 176, 336 and 176
  lines; banks 0 and 1 hold the left half of the die, banks 2 and 3 the
  right. Each of the 676,224 tile bits was located with 40 bitstreams: the
  bits are numbered, and for each bit of that number two configurations
  are packed, one with the bits where it is 1 and one with the bits where
  it is 0. Every tile bit lands on exactly one CRAM bit. A tile is a
  `rows` x `cols` layout at an origin, and all tiles of a kind in a bank
  share the layout (36 layouts). 32,384 CRAM bits belong to no tile.
- **Block RAM**: banks of 256 lines, 160 or 80 bits wide. Word w of an EBR
  is on line w, at a fixed 16-bit column per EBR, found the same way.
- **Extra bits**: `.extra_bit B P L` sets bank B, line L, position P, and
  `icepack -u` gives back the ones outside tiles.
- **Fingerprints**: 16 random configurations. Epitome's own packer
  (`bitstream.rs`) makes the same bytes as `icepack` for each, and their
  lengths and hashes are kept, so the packer can be checked without
  `icepack`.

### What the icebox experiments found

These experiments route one logic cell of tile (8, 1) to package pins
(routes found by a search of the chipdb's switches). Then they set bits and
read what `icebox_vlog` prints.

- **LUT**: each of a cell's 20 bits, set alone. 16 of them each make the
  LUT true for exactly one input value; that value is the bit's LUT index,
  with index i = in_0 + 2 in_1 + 4 in_2 + 8 in_3. All 8 cells were tried.
- **Options**: `icebox_explain` names the other 4 bits: `CarryEnable`,
  `DffEnable`, `Set_NoReset` and `AsyncSetReset`.
- **Flip-flop**: the Verilog statement for each setting of `Set_NoReset`,
  `AsyncSetReset` and the tile's `NegClk`. The flip-flop is enabled by
  `cen`. Set/reset `sr` is synchronous unless `AsyncSetReset` is set; it
  sets the flip-flop to 1 with `Set_NoReset` and to 0 without it. `NegClk`
  clocks on the falling edge.
- **Carry**: `co = (in_1 & in_2) | ((in_1 | in_2) & ci)`. `CarryInSet`
  makes the first cell's carry in 1.
- **I/O cell**: one I/O cell on the top edge has every port wired. For each
  of the 64 settings of its `PINTYPE_0..5` bits, `icebox_vlog`'s statements
  for it are recorded, with its nets named by port. The table is the same
  for both parts. It covers plain, registered and latched inputs, the DDR
  input, and plain, registered, DDR, inverted and tristate outputs (the
  output enable plain or registered). `PINTYPE_0` alone is a plain input;
  `PINTYPE_3` and `PINTYPE_4` make a plain output.
- **Block RAM**: one RAM has its ports wired, in three groups because there
  is not enough local routing for all of them at once. `icebox_vlog`
  renders the RAM as Lattice's `SB_RAM40_4K`, with nothing set and then
  with each `RamConfig`/`RamCascade` function alone:
  - `CBIT_1:CBIT_0` is `WRITE_MODE` and `CBIT_3:CBIT_2` is `READ_MODE`.
    Lattice's documentation gives the meaning of those parameters (256x16,
    512x8, 1024x4, 2048x2).
  - The cascade bits change nothing vlog shows.
  - On the LP1K a set `PowerUp` removes the RAM. On the UP5K the RAM is
    there only with `PowerUp` set.
  - Each port bit's net and each unrouted port's value are recorded:
    `RE`, `WE`, the addresses, data and mask read 0, and the clock enables
    read 1.

### What the board showed

The board is an iCESugar-nano on Amy's desk. `icesprog -p` reports
"iCESugar-Nano" with a W25Q32 flash. The experiments are in `board.rs` and
are run with:

```bash
cargo run --release -p epitome-sv --example ice40_board
```

**Method.** Each experiment is a design made from this description, packed
by Epitome's own packer, and written to the flash with MuseLab's
`icesprog`. `icesprog` is built from source (`Icesprog::install`) and run
only as a black box, over the iCELink's USB HID interface. Copying to the
iCELink's USB drive hung macOS's FAT driver twice, so the drive is not
used.

**Wiring.** The board's schematic and pin file give the wiring:
- the iCELink's UART transmit drives A3;
- B3 goes to the iCELink's UART receive;
- D1 carries the iCELink's 12 MHz clock;
- B6 drives the LED.

So the FPGA only ever drives B3. Each design makes B3 a function of A3,
through the logic under test. The Mac sends 64 bytes at 115200 baud over the
iCELink's serial port and looks at what comes back: an echo, silence, or
other bytes.

`record-board.txt` holds 176 experiments. Each one's bitstream hash is
recorded, so `board_record_agrees` can check that the description still
makes the same designs. All seventeen findings in the description's `board`
section held:
- Each of the 8 logic cells' LUTs, and each of their 4 inputs, is where the
  description says.
- An unrouted LUT input reads 0.
- Setting `IoCtrl.IE` turns a pin's input off; `REN` does not stop a driven
  input.
- A global network reaches a tile only through its column buffer, which
  needs `ColBufCtrl` set in the tile the chipdb's `colbuf` names. Without
  it, a flip-flop never clocks.
- The flip-flop clocks from D1 through global network 1, with
  `padin_glb_netwk.1` set, on either edge.
- An unrouted clock enable reads 1, and an unrouted set/reset reads 0.
- The carry formula holds: with `CarryInSet` the first cell's carry in
  is 1, and without it, 0.
- A block RAM reads its `.ram_data` contents: word 1 is read at RADDR[0] =
  A3, clocked from D1, with `RE` driven to 1. Each `RDATA` bit is the
  word's bit of the same number.
- `PowerUp` set turns the LP1K's RAM off, and an unrouted `RE` reads 0, as
  icebox_vlog says.
- The write port works: A3 is written into word 0 every clock and read
  back. `MASK[0]` set stops that bit being written; unrouted, it reads 0.

**The RAM's other modes.** These were mapped on the board with the
`--ram-modes` option of `ice40_board`; the points are in
`record-ram-modes.txt`.
- **Method.** B3 = A3 AND RDATA[pin], with the read address held constant,
  echoes exactly when the RAM gives a 1 on that pin. Twelve contents
  patterns, one per bit of the stored bit's number, read off which of the
  4096 stored bits it is. Two more probes check the answer: that bit alone
  echoes, and every other bit does not. Within a known word, four patterns
  are enough.
- **Self-check.** The method was first checked on 256x16, where it found
  word 1 bit 5 as it should.
- **Result.** For read modes 1 to 3 (512x8, 1024x4, 2048x2, from
  `CBIT_3:CBIT_2`):
  - the word is the address's low eight bits;
  - the data pins are those with `pin % 2^m = 2^(m-1) - 1`: the even pins,
    then 1, 5, 9 and 13, then 3 and 11;
  - each data pin reads bit `(pin with its low m bits clear) + (address >> 8)`
    (`board::ram_mode_bit`);
  - the other pins show the stages of a multiplexer tree on the high
    address bits.
- **Checks.** Every mapped point, in all three modes and across the high
  address bits, gives the formula's bit; `ram_modes_follow_the_formula`
  checks this. The `ram-mode*` experiments in the main suite predict from
  the formula: each mode's read, and its write (`CBIT_1:CBIT_0`), which
  lands where the read finds it and not on the neighbouring bit.

**The RAM cascade bits.** icebox_vlog shows `RamCascade.CBIT_4..7` changing
nothing. On the board, two RAMs were tried:
- **Setup.** One RAM is the RAM used throughout, and the other is the one
  below it in its column. They hold opposite contents, so which one is
  being read shows in the echo.
- **Bits tried.** Each bit alone and all four, set in either RAM.
- **What was driven and watched.** Each RAM's read or write port, watching
  each RAM.
- **Pairs.** Bits set in both RAMs at once, including `CBIT_6` in the RAM
  watched with the others in the RAM driven.
- **Pins.** Other data pins as well as `RDATA[0]`.

What they show:
- `CBIT_6` stops a RAM reading through its own ports, on every data pin,
  in either RAM.
- `CBIT_4`, `5` and `7`, alone or together, change nothing a RAM's own read
  or write shows; nor does `CBIT_6` for writing.
- No setting tried lets one RAM read or write through the other's ports.

What a cascade connects, if anything, is still unknown.

## Coverage

The JSON's `coverage` and `checks` sections hold the exact numbers for each
part. Everything below is for the UP5K unless it says otherwise. All the
checks pass, for both parts:

- The datasheet's counts match: 5,280 LUTs, 30 EBRs, 4 SPRAMs, 8 MAC16s, 1
  PLL, 2 I2C, 2 SPI, HFOSC, LFOSC, the RGB driver, and 39 I/O on SG48.
- The chipdb's grid and tiles are the experiments'.
- Every chipdb tile bit lies inside the experiments' tiles.
- The chipdb's 8 extra bits (the global networks' pad inputs) are among the
  CRAM bits the experiments found in no tile.
- Each cell's LUT and option bits are the chipdb's `LC_k` bits.

**Mapped by experiment**

- The tile grid.
- The whole bitstream format.
- Where every tile bit and block RAM bit goes.
- The packer and unpacker.
- The logic cell: the order of its LUT bits, its flip-flop options and its
  carry.

**Taken from the chipdb, with checks against the experiments**

- **Tile functions**: every tile kind's non-routing settings, by IceStorm's
  names. These cover IO pin types and controls, RAM configuration, the DSP
  and PLL settings, column buffer controls, `NegClk` and `CarryInSet`.
- **Pin map**: SG48 package pin to IO tile and PIO, for 39 pins (and the
  UWG30 package's 21).
- **Global networks**: the 8 global networks' sources (`gbufin` and
  `gbufpin`), their pad-input bits, column buffers, IO latch and IE/REN
  pairs.
- **Special cells** (26): the 8 MAC16s, 4 SPRAMs, PLL, HFOSC, LFOSC, 2 I2C,
  2 SPI, the RGB driver, LEDDA_IP, 2 IO_I3C, 2 FILTER_50NS and WARMBOOT,
  each with its ports.
- **Routing**: all 103,383 nets and 201,460 switches. Each tile's switches
  fall into one of 32 switch boxes. Each net is one of 992 shapes, placed
  by rectangles. `Routing::expand` gives the chipdb's nets and switches
  back exactly, which a test checks.

**The LP1K** has the same coverage, at its own size:
- 1,280 LUTs and 16 block RAMs, as its datasheet says;
- 27,682 nets and 53,808 switches in 37 switch boxes;
- CM36 package pins mapped to PIOs for 25 pins;
- a PLL and WARMBOOT;
- logic cell experiments that find the same bits and statements as on the
  UP5K.

**Not mapped**

- 32,376 CRAM bits outside tiles that nothing names.
- Tile bits with no function or switch: 57 per logic tile, for example. The
  JSON lists each kind.
- The DSP (UP5K only) and PLL settings, which are only named. The LP1K's
  PLL is not in its CM36 package; the chipdb lists CM36 under the PLL's
  `LOCKED` packages.
- What the RAM cascade bits connect. On the board, `CBIT_6` stops a RAM's
  own read, and nothing tried made two RAMs work together.
- The routing has been checked against the device only through the
  designs the flow put on the board (see the flow above), and through
  the icebox experiments' routes reading back as intended.
- The full-size iCESugar (UP5K) has not been tried on a board. Only the
  iCESugar-nano's LP1K has.
- Timing.
